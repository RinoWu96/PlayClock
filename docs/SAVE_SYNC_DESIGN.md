# Ryujinx 存档云同步 · 设计稿

状态：设计稿 v2（2026-10-17）；S1–S5 已实现（分支 `feature/save-sync`），真机测试进行中。范围只有 **Ryujinx**，场景是 **Windows 电脑 ↔ Steam Deck**。存储先用用户自己的**坚果云**（WebDAV），预留 **OneDrive**。

已确认的决定（2026-10-17）：
- 云端每个游戏保留 **5 个**历史版本；同步程序可以写 `PlayClock/saves/ryujinx/**`，并且只删除自己建的、超出 5 个的旧版本。
- **自动恢复**：只有云端变了时，自动用云端存档覆盖本机（覆盖前先备份）。
- 时机参考 **Steam 云存档**：启动前下载、退出后上传、冲突让用户选、息屏时不做事（第 7 节）。
- Deck 上游戏开着时，存档变化**最多每 15 分钟上传一次**；本月上传超过额度 70% 时自动降级为「只在退出时上传」。
- 先用坚果云；存储做成独立的一层，以后可以加 OneDrive（第 13 节）。

## 1. 目标和不做的事

**要做到**
- 在一台设备上玩完，另一台设备开玩时拿到的是最新存档，不用手动拷文件。
- 任何情况下都不丢存档：覆盖本机存档前一定先备份，云端保留历史版本。
- 两台设备都玩过、谁也不是谁的延续时（冲突），不自动覆盖，让用户选。

**不做**
- 即时存档（Ryujinx 没有）、着色器缓存、Mod、固件、密钥（`prod.keys` / `title.keys` 绝不读取、绝不上传）。
- `bis/system` 下的系统存档、BCAT / 缓存类存档。
- Ryujinx 以外的模拟器（结构不同，以后另行设计）。

## 2. 已确认的 Ryujinx 存档格式（2026-10-17 在用户电脑上只读查看）

```
%APPDATA%\Ryujinx\                      Deck: ~/.config/Ryujinx/（EmuDeck 的 AppImage）或便携目录
  bis\user\save\0000000000000001\        ← 编号按「第一次启动」分配，不同设备上同一游戏编号不同
      0\  …存档文件…                     ← 已提交的存档（以它为准）
      1\  …                              ← 工作副本；实测 7 个存档都与 0 完全相同
      ExtraData0, ExtraData1             ← 元数据
  bis\system\save\8000000000000000\0\imkvdb.arc   ← 「编号 ↔ 游戏」索引（我们不写它）
  system\Profiles.json                   ← 用户档案；默认 RyuPlayer，user_id 00000000000000010000000000000000
  games\<title id>\gui\metadata.json     ← 游戏名（"title"）、Ryujinx 自己记的时长
```

`ExtraData0` 的前 0x70 字节（小端）：

| 偏移 | 长度 | 含义 | 实例（编号 0001） |
|---|---|---|---|
| 0x00 | 8 | 游戏 ID（program id） | `00a0 1202 3095 0001` → `010095300212A000` |
| 0x08 | 16 | 用户 ID | `0100…0000` → `00000000000000010000000000000000` |
| 0x20 | 1 | 存档类型：1 = 账号存档，3 = 设备存档 | `01` |
| 0x40 | 8 | 拥有者 ID（= 游戏 ID） | |
| 0x58 / 0x60 | 8 / 8 | 数据大小上限 / 日志大小上限 | |

所以：**读 ExtraData0 就能把本机的编号目录对应到游戏 ID**，不需要解析 `imkvdb.arc`。

**实测大小**（`0\` 目录，zip 压缩后）：

| 存档 | 文件数 | 原始 | 压缩后 |
|---|---|---|---|
| 最大的一个 | 19 | 1.03 MB | 0.46 MB |
| 带游戏内相册的一个 | 11 | 3.01 MB | 0.38 MB |
| 其余 5 个 | 1–5 | 0–1.74 MB | 0.01–0.15 MB |
| **合计 7 个** | | 8.2 MB | **1.1 MB** |

## 3. 同步什么、按什么对应

- **同步单位**：一个游戏的一份账号存档（类型 1），属于本机当前用户档案（`Profiles.json` 里状态为 Open 的那个；有多个档案时在设置里选，默认 RyuPlayer）。设备存档（类型 3）以后再加，扫描到时提示「暂不支持」。
- **对应关系**：按 **游戏 ID** 对应，与本机编号无关。上传时从 ExtraData0 读游戏 ID；恢复时在目标设备上找「游戏 ID + 用户 ID + 类型」相同的编号目录。
- **内容指纹**：对 `0\` 目录做 SHA-256：按相对路径排序，依次把「路径、大小、文件内容的 SHA-256」喂进去。不包含 ExtraData（它在每台设备上本来就不同）。同步判断全部用指纹，**不依赖两台设备的时钟**；时间只用来显示。

## 4. 云端布局

```
PlayClock/saves/ryujinx/<游戏ID>/
    head.json                                          ← 当前「最新」是哪个版本
    v-20261017T093000Z-<设备>-<指纹前8位>.zip           ← 历史版本，保留最近 5 个
    conflict-20261017T101500Z-<设备>-<指纹前8位>.zip    ← 冲突时另一台设备的版本，等用户选
```

- zip 里：`save/…`（`0\` 目录的全部文件）+ `meta.json`（游戏 ID、游戏名、用户 ID、指纹、大小、设备、时间、Ryujinx 版本）。
- `head.json`：
  ```json
  {"hash": "…", "file": "v-….zip", "device": "…", "device_name": "RHINO",
   "time": 1792000000, "size": 482304, "game": "…", "supersedes": ["<被用户放弃的指纹>", "…"]}
  ```
  `supersedes` 记录用户解决冲突时**放弃**的那些版本的指纹；另一台设备看到自己的指纹在里面，就知道应该改用云端版本（第 6 节）。
- **写入顺序**：先上传版本 zip（文件名唯一，不会互相覆盖），再写 `head.json`。写之前记下 `head.json` 的版本标记（ETag），写的时候带 `If-Match`；如果存储不支持（坚果云待实测），写完再读一次确认是自己写的，否则按冲突处理。
- **删除**：只删本程序自己的 `v-*.zip` 中超出 5 个的最旧版本；`conflict-*.zip` 在冲突解决后删除。`saves/` 以外的文件和规则不变：仍然只写 `devices/`、`summary.json`、`covers/`。

## 5. 本机状态

每台设备记一个小文件：电脑在 `data\save_sync.json`，Deck 在 `~/.config/playclock/save_sync.json`。

```json
{"games": {"010095300212A000": {"base": "<上次和云端一致时的指纹>", "index": "0000000000000001",
                                "scan": {"mtime": 1792000000.5, "size": 1413120, "hash": "…"},
                                "last_upload": 1792000000, "pending_upload": false}},
 "traffic": {"month": "2026-10", "up": 12345678, "down": 2345678}}
```

- `base`：这台设备上次和云端一致时的指纹，是判断「谁改过」的依据。
- `scan`：缓存；目录的修改时间和大小都没变就不重新算指纹（扫描几乎不读文件）。
- `pending_upload`：要传但还没传成功（比如 Deck 退出游戏后马上息屏），下次醒来先补传。
- `traffic`：本程序自己统计的本月上传 / 下载字节数（第 11 节）。

## 6. 判断规则（每个游戏）

记号：**L** = 本机现在的指纹，**B** = base，**R** = 云端 head 的指纹。

| 情况 | 动作 |
|---|---|
| 云端没有，本机有 | 上传，B = L |
| L = R | 已同步，B = R |
| L = B，R ≠ B（只有云端变了） | **自动从云端恢复**（先备份本机），B = R |
| L ≠ B，R = B（只有本机变了） | **上传**，B = L |
| L ≠ B，R ≠ B，L ≠ R，且 L 在 R 的 `supersedes` 里 | 用户已经选了云端版本：按「从云端恢复」处理 |
| L ≠ B，R ≠ B，L ≠ R（两边都变了） | **冲突**：不动本机存档，把本机版本传成 `conflict-*.zip`，等用户选 |
| 本机还没有这个游戏的存档目录，云端有 | 不能凭空创建（不写 `imkvdb.arc`）：提示「先在本机启动一次这个游戏，再同步」 |
| B 为空（第一次在这台设备开启同步），L、R 都有且不同 | 按冲突处理（不知道谁是谁的延续） |

第一次在 Deck 上开启时，Deck 上随手开过一次的游戏会是新存档，会列为冲突，在电脑上选「用云端的」就行。

## 7. 什么时候做（参考 Steam 云存档）

Steam 的做法：游戏由 Steam 启动，所以**启动前先下载、进程退出后上传**；两边都改过就弹窗让用户选；Deck 息屏时，只有专门适配了 Dynamic Cloud Sync 的游戏会在息屏前上传、唤醒时下载，其余游戏只提示「先回 Deck 把游戏关掉」。Ryujinx 里的游戏无法在唤醒后重新读档，所以我们照搬前三条，第四条用「存档变化时限频上传」折中。

| 时机 | 电脑 | Deck |
|---|---|---|
| **开玩前下载** | PlayClock 启动时；Ryujinx 关闭时；另一台设备同步后、且它**没开游戏**（刚关闭）或**报告了游戏中的上传**（`open_game.saved` 变化，Deck 最多每 15 分钟一次）时；每天一次；点「立即同步」时（实现时为安全起见，只在 Ryujinx **完全关闭**时恢复；Ryujinx 开着时云端有新存档会提醒先关闭） | **启动守卫**：Ryujinx 进程一出现（每秒检查新进程），先暂停它（SIGSTOP），检查云端、需要的话恢复存档，再让它继续（SIGCONT），一般只多一两秒；如果最近 1 分钟内刚检查过就不暂停。效果等同 Steam 的「启动前下载」，而且**不用改 Steam 快捷方式**（原计划的 `%command%` 包装不再需要）。另外 Ryujinx 退出后、唤醒后各检查一次 |
| **退出后上传** | Ryujinx 游戏会话结束 + 10 秒，只传这一个游戏 | 同左 |
| **玩的过程中** | 不传 | 存档内容变了才传，**同一个游戏最多每 15 分钟一次**：直接息屏也最多只丢最后 15 分钟的进度 |
| **息屏期间** | — | 什么都不做（进程被冻结）；醒来后先补传 `pending_upload`，再做「开玩前下载」的检查 |
| **兜底** | 每天一次全量检查（只对指纹变了的游戏发请求） | 唤醒后一次全量检查 |

- **恢复只在没有游戏运行时进行**：Ryujinx 进程不存在，或者 Ryujinx 开着但停在游戏列表（窗口标题 / 日志表明没有加载游戏）。后一种情况是否安全要在真机测试第 2 步验证，验证不过就退回「只在 Ryujinx 关闭时恢复」。写入前最后一刻再检查一次。
- **「还开着」提醒**：每台设备把「正在运行的游戏」写进自己的设备文件（`open_game: {"id": "…", "since": …, "saved": 上次游戏中上传的时间}`，游戏退出时清空；游戏中上传存档后马上同步一次设备文件，电脑据此去拿新存档）。电脑上开一个 Ryujinx 游戏时，如果 Deck 的设备文件显示同一个游戏还开着（比如息屏中），托盘提醒：「Deck 上《XX》还开着，先在 Deck 上退出游戏，否则两边进度会冲突」。
- **以后可选**：Deck 息屏前上传一次（相当于 Dynamic Cloud Sync），利用 systemd 的「睡眠前通知」（`PrepareForSleep` + 延迟锁）。一次会话只传一次、几乎不丢进度，但要在真 Deck 上验证普通用户服务能不能拿到这个通知，所以放到 S5。

## 8. 恢复的具体步骤

1. 下载版本 zip 到临时目录，校验指纹与 `head.json` 一致，大小不超过 256 MB，zip 里没有 `..`、绝对路径之类的条目。
2. 找到本机对应的编号目录，确认 ExtraData0 的游戏 ID、用户 ID、类型都对得上，否则中止。
3. **再次确认没有游戏在运行**，否则中止，下次再试。
4. 把本机的 `0\` 打包成备份 zip（第 9 节）。
5. 解压到 `<编号>\0.new\`，然后 `0` → `0.old`，`0.new` → `0`；`1\` 同样换成相同内容；最后删掉 `.old`。ExtraData 保持不动。
6. 任何一步出错：把 `.old` 换回来，记录错误，不改 B。

## 9. 本机备份

- 每次恢复前、每次标记冲突时，把本机 `0\` 打包成 zip：
  电脑 `data\save_backups\ryujinx\<游戏ID>\<时间>.zip`，Deck `~/.local/share/playclock/save_backups/…`。
- 每个游戏保留最近 20 份（几 MB），只删本程序自己建的备份。
- 设置里可以「从备份恢复」。

## 10. 界面

**电脑（设置 → 存档同步（Ryujinx））**
- 开关（默认关）；显示检测到的 Ryujinx 数据目录（可手动修改）和用户档案；本月上传 / 下载流量。
- 游戏列表：游戏名、最后修改的设备和时间、状态（已同步 / 待上传 / 已从云端恢复 / 冲突 / 需先在本机启动一次 / 另一台设备上还开着）。
- **冲突弹窗**（照 Steam）：两边各显示设备名、时间、大小和 Ryujinx 记录的这个游戏的游玩时长；按钮「用本机的」「用云端的」。选之前自动备份本机存档。Deck 上发生的冲突也在这里解决（选完后 Deck 下次同步自动生效）。
- 每个游戏「历史版本…」：列出云端 5 个版本和本机备份，可以恢复任意一个（恢复前同样先备份）。
- 托盘通知：从云端恢复了存档、出现冲突、另一台设备上同一个游戏还开着、流量降级时各提示一次。

**Deck agent（没有界面，命令行）**
- `playclock_deck.py saves`：列出每个游戏的状态和本月流量。
- `playclock_deck.py saves use-cloud <游戏ID>` / `use-local <游戏ID>`：在桌面模式或 SSH 里也能解决冲突。
- `playclock_deck.py saves on|off|sync`：开关、立即对比一次。
- 冲突、恢复和 `open_game` 记在 agent 的设备文件里，电脑端「存档同步」页能看到 Deck 的状态。

## 11. 流量（坚果云：每月上传 1 GB、下载 2 GB）

按最大存档 0.5 MB / 次估算：

| 上传规则 | 每天玩 4 小时，每月上传 | 占额度 |
|---|---|---|
| 只在退出游戏时上传 | ≈ 30 MB | 3% |
| **加上 Deck 游戏中最多每 15 分钟一次（采用）** | ≈ 240 MB（最坏） | 24% |
| 若改成每 5 分钟一次（不采用） | ≈ 720 MB | 72% |

- 下载：另一台设备只在开玩前下载最新的一份，中间版本不下载，每月几十 MB。
- 历史版本占存储空间，不占流量。
- **自动降级**：本程序统计本月上传字节数，超过 1 GB 的 70% 时改为「只在退出游戏时上传」，并在电脑上提醒；下个月自动恢复。额度数值放在设置里，可改。

## 12. 安全护栏（实现时逐条检查）

- 只读写 `bis/user/save/<编号>/0`、`/1`，且编号目录的 ExtraData0 必须匹配游戏 ID、用户 ID、类型。
- 绝不读写 `prod.keys`、`title.keys`、固件、`bis/system`、`imkvdb.arc`。
- 有游戏在运行时绝不写存档；写之前最后一刻再检查一次。
- 覆盖前必备份；云端只删自己建的、超出 5 个的版本和已解决的冲突文件。
- 指纹不一致、大小超限、zip 内有可疑路径：一律中止。
- 第一个版本先做「只上传、不恢复」，用户确认云端版本正常之后，再打开恢复。

## 13. 存储层（坚果云，预留 OneDrive）

存档同步只通过下面这几个操作访问云端，不直接依赖 WebDAV：

```python
class Storage:
    def list(self, folder) -> dict[str, str]: ...          # 文件名 -> 版本标记
    def get(self, path) -> tuple[bytes, str]: ...           # 内容, 版本标记
    def put(self, path, data, if_match=None) -> str: ...    # 返回新版本标记；if_match 不符时抛 Conflict
    def delete(self, path) -> None: ...
    def ensure_dir(self, folder) -> None: ...
```

- **WebDAV（坚果云，现在用）**：在 `sync.py` 现有的 `WebDAV` 客户端上补 `delete` 和 `If-Match`；Deck agent 里的客户端同样补上（仍然只用标准库）。
- **OneDrive（预留，暂不实现）**：Microsoft Graph，存在应用专属文件夹 `/me/drive/special/approot`；小文件（< 4 MB）直接 `PUT …:/content`；`If-Match` 原生支持。需要：用户在 Azure 注册一个公共客户端应用（个人账户）；电脑和 Deck 各用设备代码登录一次；访问令牌每小时刷新，刷新令牌长期不用（约 90 天）会失效，需要重新登录。届时设置里「存档同步」可以单独选存储位置，游玩记录同步不受影响。
- 测试用同一套用例跑每种存储（WebDAV 用 wsgidav；OneDrive 用假的 Graph 服务器）。

## 14. 测试计划

**自动测试**（不需要真机）
- 用临时目录造两个假的 Ryujinx（编号不同、ExtraData 按第 2 节格式写），加 wsgidav 本地 WebDAV：
  - 电脑玩 → 上传 → Deck 恢复到**不同编号**的目录；内容一致、ExtraData 不变。
  - 第 6 节表格每一行一个用例（包括 `supersedes`、首次开启、本机没有存档目录）。
  - 有游戏在运行时不恢复；恢复中途出错能回滚。
  - 15 分钟限频、`pending_upload` 补传、70% 降级。
  - 只删除超出 5 个的 `v-*.zip`，不碰其他文件。
- ExtraData0 解析用用户电脑上读到的真实字节做测试数据。

**真机测试**（按顺序，每一步先备份 Ryujinx 的 `bis\user\save`）
1. 电脑：只上传，检查坚果云里的 zip 能正常打开、内容和本机一致。
2. 电脑：把自己的存档「恢复」成云端版本（同一份），分别在 Ryujinx 关闭时、停在游戏列表时各做一次，进游戏确认存档正常 —— 验证 `0` / `1` 的处理和「游戏列表时可以恢复」。
3. 电脑：从历史版本恢复一个旧存档，进游戏确认确实回到了旧进度，再恢复回来。
4. Deck：先装好 agent（还没在真机上跑过），确认 Ryujinx 数据目录，以及启动守卫（暂停 / 继续 Ryujinx）在游戏模式下没有副作用。
5. Deck 上启动一次游戏 → 同步 → 电脑上把冲突选成「用云端的」→ Deck 上进游戏确认是电脑的进度。
6. 反方向：Deck 上玩、退出 → 电脑上确认自动恢复；Deck 上玩、直接息屏 → 电脑上确认拿到 15 分钟内的进度，并出现「Deck 上还开着」提醒。

## 15. 分阶段

## 16. 风险 / 待验证

- `0` / `1` 的语义是根据 LibHac 的目录存档实现和实测「两者相同」推断的；「停在游戏列表时恢复」是否安全也未验证。真机测试第 2 步专门验证。
- Deck 上 Ryujinx 的数据目录（EmuDeck AppImage 是 `~/.config/Ryujinx`，Flatpak 是 `~/.var/app/org.ryujinx.Ryujinx/config/Ryujinx`，或便携目录）、启动守卫是否有副作用，要靠 agent 的 `doctor` 和真机测试确认。
- 坚果云 WebDAV 是否支持 `If-Match`、请求频率上限，都没有官方数字，S1 实测。
- 两台设备的 Ryujinx 版本差别很大时，存档格式由游戏决定，一般没问题；`meta.json` 记录 Ryujinx 版本，出问题时方便排查。
- Deck 退出游戏后马上息屏、网络还没传完：靠 `pending_upload` 在醒来后补传；这期间另一台设备拿不到最新进度。
